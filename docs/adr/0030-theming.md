# 0030: Theming: eleven tokens per scheme, light and dark, themes as JSON, self-hosted fonts

Status: accepted, 2026-09-12. Lands in three pull requests: the schemes and text size; themes as JSON; fonts. All three have landed.

## Context

The PWA was dark only, with eleven colour custom properties in `styles/base.css` that every component reads (the CodeMirror theme too, since custom properties inherit into a shadow root), a sixteen-colour ANSI palette as literals in `ansi/render-ansi.ts`, one root font size and the platform's system font stack. The operator asked for four things together: colours a user can set and share as plain JSON, light and dark with the system's choice as the default, a choice of fonts for text and for code, and a text size. They are one feature, theming, and were planned as one so that the first pull request leaves room for the other two.

Two constraints shape it. The relay serves a strict CSP (`default-src 'self'`, engineering.md § Security) and the PRD promises zero third parties, so nothing may be fetched from a font service at runtime. And the app must not flash: a device on a light scheme that paints dark for the moment before its choice is read is a bug on every launch.

## Decision

1. **Eleven tokens, a light and a dark value each, plus the sixteen ANSI colours.** The tokens stay what they were (`--bg`, `--fg`, `--muted`, `--panel`, `--panel-2`, `--border`, `--accent`, `--accent-fg`, `--danger`, `--ok`, `--warn`); each is written once in `base.css` as `light-dark(light, dark)` and picked by `color-scheme`, so there is one list to read and one place to change, and native controls match for free. `color-scheme` is `dark` by default, `light` under a `prefers-color-scheme: light` media rule that a `data-scheme='dark'` on the root switches off, and `light` under `data-scheme='light'`: the stylesheet alone follows the system, so the page paints right before any script runs, and the script's choice overrides it either way. `light-dark()` needs Chrome 123, Safari 17.5 or Firefox 120 (spring 2024), which the app's other platform APIs already assume. The ANSI palette becomes `--ansi-0` to `--ansi-15` the same way, and the renderer emits `var(--ansi-N)` for a named colour, so a command's output re-colours with the page; only the 256-colour cube and truecolor, where the program named an exact colour, stay literal. The light ANSI colours are darkened until every one holds 4.5:1 against the page, where a command's output sits, which brings bright green and yellow close to their normal ones; a terminal-bright palette would not read on a light page. Black scrims and shadows (`rgb(0 0 0 / 40%)` and the like) stay literal too: they are darkness over whatever is there and read on either scheme.

2. **Scheme and text size are the device's, kept in `localStorage`, applied before mount.** `appearance/appearance.ts` holds the choices (`mode`: `system`, `light` or `dark`; `fontSize`: whole pixels, 12 to 22, 15 by default) behind a reactive object with setters, a guard that takes a stored value whole or falls back to the defaults, and the scheme in force as a computed (the choice, or the system's through `prefers-color-scheme` while the choice is `system`). They are not kept in the store's storage like the notification sound and the send key are: that is IndexedDB, read after the app is on screen, and both of these decide the first paint. `app-appearance.ts` binds the module to `localStorage` and `matchMedia`; `main.ts` runs `apply-appearance.ts` on the document before `createApp`, and it keeps `data-scheme`, the root font size and the `theme-color` metas (so a phone's status bar matches; one meta per scheme in the markup for the paint before the script, both set to the page's resolved background after) in step from then on. The store carries the same object to the views as `store.appearance`, a `StoreOptions` the browser builds before the store: the store does nothing with it, it is the one thing every view already holds. Every size in the app outside the Home page is em- or rem-based, so the root font size scales the whole thing, the editors included (their `13px` became `0.87rem`). CodeMirror's own `&dark`/`&light` rules are chosen by a flag on the theme, so there is a theme per scheme, built once each, and an editor swaps them through a compartment when the scheme changes under it: in system mode the device flips at dusk with a diff open.

3. **A theme is one JSON object, shared by copy and paste** (second pull request). It names itself and carries a `dark` and a `light` set of the eleven tokens, optionally the sixteen ANSI colours per scheme (all sixteen or none: a command names them by number), and, from the third pull request, the two font families. Either set, and any token in it, may be left out and keeps the default's value, so a theme can be as small as one accent; but every key must be one the app knows, since a misspelt token silently ignored is a theme that "does not work" with nothing to say why. Colours are hex only, `#rgb`, `#rrggbb` or `#rrggbbaa`: every palette in the wild is published that way, one pattern checks it without a browser, and nothing that is not a colour can ride into the stylesheet. A theme that does not parse is refused whole, with a reason naming the key, not repaired. Stored on the device beside the scheme and size (`appearance/theme.ts` holds the format and the default, `presets.ts` the presets), never on the box: a phone and a laptop of one operator may want different looks, and sharing is copying the JSON out of Settings and pasting it in on the other device; a preset chosen is stored as its own copy, so a shared theme is always the whole thing. The app ships a default theme, which is exactly the two sets in `base.css`, and two presets, Nord and Solarized, as much to show what the JSON looks like as to be chosen. A theme applies as custom properties on the root, one `light-dark()` pair per token like the stylesheet's own, the default's value filling either side the theme left out (a pair needs both, and a stylesheet cannot be asked for one side of its own); the default is applied the same way rather than by taking the properties off again, so Default is one more theme, not a second path.

4. **Fonts are self-hosted and chosen from a fixed list** (third pull request). Ten families for text and ten for code (`appearance/fonts.ts`), `@font-face` declarations in `styles/fonts.css` over woff2 files under `public/fonts`, each family's OFL beside it. Each file is the Latin block Google Fonts serves for the family, fetched once and committed: one variable file where the family has a weight axis, else each static weight the family has, upright only, since the app uses four weights and no italic face of its own, and a browser slants the upright for Markdown's emphasis. A browser downloads a face only when something on the page uses it, so the list costs nothing until a family is chosen. No font service: the CSP and the third-party promise hold, and there is no request to Google when the app opens. The stylesheet paints with two custom properties, `--font-text` and `--font-code`, the platform's own stacks, and the choice sets each to a shipped family ahead of that stack. The choice is the device's own, kept beside the theme rather than inside it (`fonts` in the stored value, absent when neither is chosen, like the default theme): picking a preset and picking a family are the two controls they look like, and Default stays no theme at all whatever font is chosen. The families ride in the theme JSON as `fonts` (`text`, `code`) so that a shared theme carries them: Copy folds the device's choice in, and Paste takes the pasted theme's out and applies it, or takes the choice away when the JSON names none, since a shared theme is always the whole thing. A family is any name, since the device the JSON came from may ship one this one does not: that family is shown as chosen and marked in Settings, the page falls back to the platform stack, and the rest of the theme holds.

## Consequences

- `styles/base.css` grows a light value per token and the ANSI tokens; it was already past the 300-line smell and is now further past it. The tokens are the price of one global stylesheet (engineering.md § Vue); the spinner and the Markdown rules are the candidates should it need splitting.
- Settings gains an Appearance section, distinct from This device although it is the device's too, because it grows to hold the theme and the fonts. The store carries the appearance to the views (`store.appearance`, a `StoreOptions` the browser builds before the store), so a component reaches it the way it reaches everything else, and a test hands in one over a map.
- The Home page (the unpaired landing) keeps its own green scheme in `oklch` and is out of scope: it is the product's face, not the operator's tool. It pins `color-scheme: dark` so its controls stay dark under a light system; the status bar over it follows the page background, which on a light system is light, until the landing is given a look of its own.
- The stored value is taken whole or not at all. The theme is stored in the same key, and Default as no `theme` key, which is also what a device that chose a scheme before there were themes has stored: it keeps that choice through the upgrade. A stored theme that does not parse takes the whole value down to the defaults, like a bad size does.
- The presets' dark sides are their palettes as published, contrast included: Nord's red on its own background is 3:1, Solarized is famously low-contrast, and a "Solarized" that read at 4.5:1 throughout would not be Solarized; only a colour that would vanish outright (Solarized's bright black is its own page) is swapped for the palette's next grey. The light sides are derived, since both palettes were drawn for a dark terminal and their colours do not read on a light page: each is darkened in its own hue until it holds 4.5:1 against the light page, the ANSI colours included, and Solarized's whites, which are its light page, become its darks. Where a palette has no colour for a token (Nord no mid grey for muted text, Solarized no third background) the nearest mix in its own hues stands in.
- The default theme in `theme.ts` repeats the values in `base.css`: a `?raw` import of the stylesheet comes back empty under Vitest, and browser code may not read a file, so no test can compare them. `.github/scripts/check-theme-default.sh`, run by `pnpm run check`, reads both and refuses a pair that differs. The platform font stacks in `fonts.ts` repeat `base.css` the same way, and the families it lists must each have a face in `fonts.css`, a file and a licence under `public/fonts`: `check-fonts.sh` refuses any of it missing.
- The font files are 720 KB of woff2 in the repository, Playpen Sans alone 190 KB (a handwriting face with many alternates); a device downloads only the family it chose. The landing's two families are among the twenty, declared in the same stylesheet.
- Three families have no bold at all upstream (Fragment Mono, Nova Mono, Oldenburg), so with one of them chosen the app's headings, buttons and Markdown's strong text are the browser's own emboldening of the regular, which is heavier and rougher than a drawn bold. Accepted: each is offered for its regular, and a synthesised bold is what every browser does for a font without one.
- A chosen family, like a theme, is applied by the app bundle after the stylesheet has painted, so a device with one sees the platform font for that moment and the text reflows; the same cause and the same fix as the theme's flash above.
- Google's Latin block has no box drawing or block elements, and the subset files cannot be widened after the fact, so with a code family chosen a tree, a table or a progress bar a command draws is lettered in that family and ruled in the platform's mono, at a different advance width, and its columns may not line up. Accepted: those are a minority of lines, and the platform mono is what every line had before; a family's full file, at three to five times the size, is the trade if it shows.
- A theme is applied by the app bundle, which runs after the stylesheet has painted, so a device on a theme sees the default's background for the moment before the bundle runs; with the bundle in the service worker's cache that is a frame, and the CSP (`default-src 'self'`, no inline script) rules out the usual inline fix. A scheme does not flash, since the stylesheet resolves it alone. Accepted for now; a small appearance-only entry module ahead of the app bundle is the fix if it shows.
- A theme's name is capped at 64 characters: it is what the picker shows, and a paste is the one place a length nobody typed can come from.
- The `theme-color` metas are re-read on a theme change as well as a scheme change, since a theme changes the page background as much as a scheme does; the e2e flow chooses Nord and checks the page and the status bar followed and both survive a reload.
- Paste reads the clipboard through `navigator.clipboard.readText`, which is missing off HTTPS and asks the operator's leave (a permission on Chrome, a Paste callout on iOS); a clipboard that cannot be read is said so on the status line, not thrown. There is no text box to edit a theme in: editing JSON on a phone is what a text editor and the clipboard are for.
- The e2e flow chooses Light in Settings alongside the send key, checks the status-bar colour followed, and that the scheme survives a reload.
- `index.html` keeps `apple-mobile-web-app-status-bar-style` at `black-translucent`, which paints iOS's clock and battery white whatever the page: on the light scheme they will be hard to read in the installed app until that meta is revisited on a device. The manifest's `theme_color` and `background_color` stay dark, so the install splash is dark for everyone.
- Anyone reading `render-ansi.ts` output in a test sees `var(--ansi-1)` where `#f7768e` was.
