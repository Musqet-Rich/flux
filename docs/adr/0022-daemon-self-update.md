# 0022: Daemon self-update: a signed bundle, verified with node:crypto, installed then re-executed in place; supervised by systemd or launchd

Status: accepted, 2026-08-30.

## Context

ADR 0021 makes the user update their own daemon from the PWA. That update runs on a box the project cannot see, replaces the code that talks to the operator's own agents, and fetches over the public internet. So it must be safe to trigger blindly: a tampered or truncated download must be refused, not run. The daemon build helps — `tsdown` inlines every dependency, so `apps/daemon/dist` is three self-contained `.mjs` files, ~200 KB total, with no `node_modules` at runtime. An update is therefore a matter of swapping three files, not rebuilding, and integrity is a matter of signing three files.

The daemon must also _stay_ running: always-on, restart on crash, start on reboot, on both Linux and macOS. Today only a systemd unit exists (Linux). Supervision belongs outside the daemon; the daemon stays a plain process.

## Decision

1. **Signed bundle, no archive format.** A release's daemon artifact is a `manifest.json` — `{ version, files: [{ name, sha256 }] }` — the raw `.mjs` files it lists, and a detached signature over the manifest bytes. No tar, no gzip: the daemon fetches the manifest, verifies the signature, fetches each listed file and checks its SHA-256 against the manifest. This keeps the whole path on Node built-ins (`fetch`, `node:crypto`) with **no new dependency** (engineering.md § Dependencies), and each file is small enough to hold in memory and hash whole.

2. **ed25519, offline keys, a trusted set vendored in the daemon.** The manifest is signed with an ed25519 key **held offline by the release signer and never placed in CI**; CI uploads the already-signed artifact. The daemon ships a **set of trusted public keys** as a source constant and accepts a manifest signed by **any one** of them (`crypto.verify(null, manifest, key, signature)` over the set until one verifies). 1.0 ships trusting three independent keys — one live signer, two spares kept offline — so a lost or destroyed signing machine is recovered by signing the next release with a spare the daemons already trust, with no scramble to re-key. A signature that verifies under no trusted key, or any file whose hash does not match the signed manifest, aborts the update with `bad_signature` — the running daemon is untouched. This is the guarantee that makes a phone-triggered update safe: the box runs only bytes one of the offline keys signed.

3. **Fetch, verify, stage, atomically swap, then re-exec in place.** The daemon downloads to a temp directory under its data dir, verifies everything there, then renames each file over its own installed path (rename is atomic within a filesystem; a crash mid-update leaves either the old or the new file, never a torn one). It then re-executes itself with `process.execPath` and its original argv (an `execve`, so the **PID is unchanged**). The existing bounded shutdown (ADR 0017) stops in-flight agents first. Because the PID persists, neither systemd nor launchd sees a restart, no privileged `systemctl`/`launchctl` call is needed, and the path is identical with or without a supervisor (a bare devcontainer works the same). A daemon launched from a source checkout (dev) refuses to self-update and says so; self-update installs only over an installed bundle.

4. **The target version comes from the RPC; downgrades and same-version are refused.** `daemon.update { version }` names the release to install (the PWA passes its own version, ADR 0021). The daemon fetches that release's manifest from GitHub Releases, verifies it, and refuses a version equal to or below its own (`already_current`) or below the compat floor. The signature covers the version, so the daemon cannot be steered to an unsigned or forged build regardless of what the RPC asks for.

5. **Progress as events, completion as reconnect.** The daemon emits `update.progress { phase }` for `fetching`, `verifying`, `installing`, `restarting`, and `update.failed { reason }` on any abort (`bad_signature`, `download_failed`, `already_current`, `unsupported`, `disk_error`). Success has no event: the daemon re-execs, the channel drops, and the device reconnects and reads the new `version` from `hello`. The PWA shows the phases, then "reconnecting", then the new version.

6. **Supervision is host-provided; `flux service install` writes the right manifest.** The daemon is platform-neutral; a new subcommand detects the host and installs the supervisor:
   - **Linux → systemd.** The existing hardened unit (`deploy/flux-daemon.service`), a system service running as the `flux` user, `enable --now`, `WantedBy=multi-user.target` for start-on-boot.
   - **macOS → launchd.** A **LaunchAgent** at `~/Library/LaunchAgents/com.flux.daemon.plist` with `RunAtLoad` and `KeepAlive`, run as the logged-in user so the agents inherit that user's keychain, PATH and `claude`/`gh` logins. It runs while that user is logged in; a headless Mac that must run before login uses a root LaunchDaemon instead, documented with the caveat that it loses the user's GUI session and keychain. launchd offers almost none of systemd's confinement knobs, so the macOS install is "runs as you, lightly sandboxed" — acceptable because the agents sandbox themselves and the systemd unit already forgoes syscall filtering for the same reason.
   - **No init system (typical devcontainer).** No supervisor to install: the subcommand prints the run command (or writes a `start.sh`) and the container's own restart policy keeps it alive. Self-update still works via the in-place re-exec.

## Consequences

- The whole update path is Node built-ins: `fetch` for the download, `node:crypto` for ed25519 and SHA-256, `node:fs` for the atomic renames. No archive library, no signing library, no new dependency.
- The security of the update reduces to custody of the offline ed25519 keys. Compromise of **any one** key lets an attacker sign an update the daemon will run, so each key needs real custody; a CI or repo compromise cannot sign, because no key is there. The trusted set makes availability and revocation independent: losing a key costs nothing (sign with a spare), and dropping a _compromised_ key means shipping a release, signed by a surviving key, whose daemon no longer trusts the bad one — but that revocation reaches only daemons that update before the compromised key is used against those that have not. Adding a key to the set later has the same reach limit. This is why the set is fixed at three from 1.0 and why the spares are generated now, offline, not minted after an incident.
- The daemon can update itself but never downgrade or cross the compat floor, and only over an installed bundle, so a dev checkout and an installed box behave differently by design.
- Supervision is two small platform templates plus a detector, not a portable service abstraction. A third platform (Windows, a non-systemd Linux) is a new template, not a redesign.
- The re-exec keeps the PID, so a supervisor's restart counters and the daemon's own `daemon.lock` (ADR 0017) see continuity, not a stop/start. An update that fails to re-exec (a corrupt swap slipped past verification) falls to the supervisor to restart, which loads whatever is now on disk — hence the atomic rename, so what is on disk is always one whole version.
