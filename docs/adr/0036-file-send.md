# 0036: The agent offers files with `flux_file_send`: a copy in the session's attachments, a `file.offered` event, a download card

Status: accepted, 2026-11-01.

## Context

ADR 0020 brought files from the phone to the box. The other direction had no path: when the operator asked an agent for a deliverable (a report, a CSV export, a rendered chart), the file sat in the worktree on the box and the only ways to reach it from a phone were the Files pane, which shows text and not a PDF or an image, or a detour through git. The channel already carries files both ways in principle (`attach.read` pages a stored file back to the device for thumbnails), the relay must stay ignorant (ADR 0003), and every frame is capped at 1 MiB.

## Decision

1. **A floor tool, `flux_file_send { path, note? }`.** It joins `flux_ask`, `flux_notify`, `flux_compact` and `flux_help` on the Flux tools floor (ADR 0008, ADR 0023 § 5): in the shared MCP server for Claude Code and opencode, and in pi's Flux extension (ADR 0016) with the same name, description and schema. It reaches the daemon over the control socket as a new `offer` request, `{ type: 'offer', session, path, note? }`, so it is agent to daemon only and adds no RPC method. The Flux system prompt gains one line: offer a file with `flux_file_send` when the operator asked for a deliverable they will want on their device, and do not offer every file touched.
2. **A copy, not a reference.** At the call the daemon copies the file into the session's attachments directory, `<dataDir>/attachments/<session>/<id>-<name>`, with the name reduced to `[A-Za-z0-9._-]` and the path checked with `inside()`, exactly as an upload is stored (ADR 0020 § 2), streaming through a file handle with the sha256 alongside. Editing or deleting the source afterwards changes nothing the operator downloads, and a file the agent offers from outside the worktree needs no access the device would not otherwise have. The row goes in the `attachments` table, complete from the start and marked by a new nullable `offered` column (added in place like the other pre-release columns; no migration is needed, since no stored shape changes).
3. **What may be offered.** Any regular file the agent's process can read: an absolute path, or one relative to the session's worktree (the agent's working directory). A missing path is `not_found`; a directory, a FIFO, a device or anything else that is not a regular file is `bad_params` (the path is opened non-blocking and the opened handle checked again, so a path swapped for a FIFO cannot hang the daemon); a file over 50 MiB is `too_large`, a cap enforced on the copied bytes too, so a file that grows mid-copy is still refused. Each refusal comes back as the tool's error, worded for the agent to read and act on. Like the rest of the floor, the tool is not subject to an Agent's tools policy (ADR 0023 § 5): an Agent denied Read can still offer any file the flux user can read. That is deliberate, since the bytes go only to the operator's paired devices and never back to the agent, which is told the stored name and size alone. 50 MiB is a new `attachment.limits.offerBytes`, the same figure as the per-message cap inbound, since one offer is one message's worth.
4. **A `file.offered` event.** `{ attachment: Attachment, note? }`, reusing ADR 0020's `Attachment` shape (`id`, `name`, `mime`, `size`, `image`). `mime` comes from the extension, the lookup a browser makes for `File.type`, so inbound and outbound files are typed alike; anything unknown is `application/octet-stream`. `image` follows `attachment.isImage`, so the device knows which offers have a thumbnail. A blank note is no note. The row is logged only after the copy, and a log that refuses it takes the copy back out, so no file sits on the box that no event names; once logged, the row is also marked sent at the event's seq, as a message's attachments are. It is top-level like `ask` and `notify` (it comes over the control socket, not the agent's stream). No push notification: an offer answers something the operator asked for, usually right before the agent reports done, which already pushes.
5. **Read back with `attach.read`.** An offered file is served to the device by the same `attach.read`, 512 KiB a page, as an inbound one; nothing about the method changes.
6. **Lifetime is an inbound attachment's.** The file lives with the session and goes when the session is deleted (`sessions.archive` with `removeWorktree`), which removes the whole attachments directory. The lazy sweep that deletes complete attachments not sent within 24 hours skips offered rows: an offered file is never "unsent", its `file.offered` event is what carries it.
7. **A download card in the timeline.** The PWA draws `file.offered` as a card on the agent's side: the thumbnail where the file is an image (fetched like a sent image's), else a file icon, then the name, the size and the note. Download fetches every page with `attach.read`, builds a Blob of the file's type, saves it through an `<a download>` on a blob URL and revokes the URL after a grace period; Share appears only where `navigator.canShare({ files })` says the browser can share a file of that type, and opens the share sheet, which is how iOS saves to Files or sends by AirDrop. The card shows progress while it fetches and the error with Retry on a failure. The bytes are kept by the card once fetched, so Share after Download does not fetch again, and a share sheet that refuses because the fetch outlasted the tap's activation says to tap again rather than failing.

## Consequences

- Protocol additions only (§ 8): one event type and one limit, no RPC method, no existing shape changed, so `protocol` stays 2. A device that predates `file.offered` shows it as an opaque row; a daemon that predates it never emits it.
- The box holds an offered file under the data directory, outside every worktree, until the session is deleted: up to 50 MiB per offer, with no cap on how many offers a session makes. The prompt line and the tool's description are what keep an agent from offering every file it touches.
- Transfer speed is the channel's, as for uploads: a 50 MiB file is 100 round trips through the relay. Fine for the reports, exports and images this is for.
- The Files pane stays what it was; a binary deliverable now has a way to the device that does not go through git.
