# 0028: The running model and effort are a logged `agent.spec`; Claude's effort is read from its transcript

Status: accepted, 2026-09-12.

## Context

ADR 0023 put the configured `model` and `effort` on `SessionSummary` and the toolbar shows them as a chip. In practice most sessions are spawned on the box's defaults, so the chip reads "Claude Code" and the operator cannot tell from the phone which model the agent is running or at what thinking level. What matters to the operator is what is _running_, not what was typed at create: a `/model` mid-session, a default that changed with an agent upgrade, or an alias (`fable`) that resolved to a dated id.

Both facts exist somewhere. Every harness names the model on its stream: Claude Code on each `message_start` (and, as configured rather than resolved, on `system/init`), pi on each assistant `message_end`. Claude Code's stream never names the effort, though — verified on 2.1.269 with `--effort` set and unset — but the transcript it writes under `~/.claude/projects/<slug>/<session id>.jsonl` (the read source ADR 0007 named for recovery, read here for the first time) carries `effort` on every top-level `assistant` line (the captured `fixtures/claude/transcript-two-turns`, 2.1.251; still so on 2.1.269), absent only for a model with no effort levels (Haiku 4.5). pi and opencode name no thinking level on their streams.

The running model already crossed the wire as `agent.context.model`, but as an ephemeral: dropped on the floor by a device that was not connected, gone on reload, and unknown for a reopened idle session until its next model call.

## Decision

1. **A new logged event, `agent.spec { model, effort? }`, is the running spec.** The mapper for each harness reports the model whenever its stream names it (`Mapped.spec`); the supervisor logs a row only when the pair differs from the last it logged for the session. The log is the source of truth (ADR 0006), so a device sees the current spec on sync, on reload and for a reopened session, with nothing new to persist on the session row. The configured `model`/`effort` stay on `SessionSummary`: they are the flags the session was spawned with, which is a different fact.

2. **Claude's effort is read from its transcript, by the adapter, at each turn's end.** `read-transcript-effort.ts` resolves the transcript path (the `cwd` the agent prints on its `init` line, slugged to `[A-Za-z0-9-]` under the agent's config directory — the daemon's `claudeDir`: `FLUX_CLAUDE_DIR`, else `CLAUDE_CONFIG_DIR`, else `~/.claude`, resolved once at start and handed to the adapter, so no test reaches a developer's own) and reads the newest top-level `assistant` line's `effort`, backwards in bounded chunks because assistant lines are followed by prompt snapshots of comparable size. The turn's end is the one moment this process's own assistant line is certainly on disk; a read at `init` would return the previous process's effort, which is wrong in exactly the flow ADR 0023 § 3 prescribes for changing it (`sessions.restart` with a new spec). The model named before that (`message_start`) is restated with the effort last read, or none. `init` is not a source: Claude prints one per prompt naming the model as configured (`claude-haiku-4-5`) where `message_start` names what the call resolved to (`claude-haiku-4-5-20251001`), and the effort in the transcript belongs to the latter; `init` names the transcript instead (its `cwd` and session id). A model named that differs from the one on record (a `/model` mid-session) drops the effort with it, since the level read was the old model's and the new one may have none: the row is the model alone until that turn's end.

3. **No effort means unknown, not none.** The supervisor logs a spec that differs from the last one in the log, where a spec without an effort only differs by its model: a fresh process restating the model before its transcript has a line, or a read that lost a race with the agent's append, never unsays the effort on record. The last row is read from the log when the supervisor is made (`EventLog.lastOfType`), so a daemon restart logs nothing new either. A missing file, a missing line or a model with no levels all read as unknown.

4. **The device shows the latest `agent.spec` as the toolbar chip, `model:effort`, and hides the row from the timeline.** The model is shortened for the chip — the `claude-` prefix and a dated snapshot's `-YYYYMMDD` dropped, `opus-4-5:high` for `claude-opus-4-5-20251101` — so the effort, the part the chip exists to show, does not end in the ellipsis on a phone-width toolbar; the whole id is on the chip's title. The harness label stands in until the agent has spoken and rides on the title after: the toolbar has room for one of them, and the operator picked the harness at create. This amends ADR 0023's display consequence (a chip of the configured harness, model and effort): the configured `model`/`effort` stay on `SessionSummary` and in the create form, but the session screen shows what runs.

## Consequences

- The chip answers "what is running?" for every session, including the common one spawned on defaults, and survives reload, reopen and a daemon restart. The first turn of a fresh Claude session logs two rows (model at its first call, model and effort at the turn's end); later turns log none unless something changes. A `/model` mid-session shows on its next call, a new `--effort` on a restart at that turn's end — until then the chip shows the effort last on record.
- The transcript read is a dependency on Claude Code's on-disk layout (path slug, line shape), the same dependency ADR 0007 took for recovery, verified here on 2.1.269 and noted in the reader. When it breaks, the chip loses the effort and nothing else: every failure reads as unknown.
- pi's spec is the model alone; opencode names no model on its stream and logs no `agent.spec`. Both gain effort when their streams say it, as a mapper change with no protocol change.
- Additive on the wire (protocol.md § 8): an older device shows the row as an opaque record, an older daemon never sends it.
