# 0037: Several daemons on one device: pairings by room id, one connection open, per-daemon cache and push

Status: accepted, 2026-11-01. Implements prd.md P3 "Multiple boxes from one PWA".

## Context

The PWA held exactly one pairing (ADR 0012), under the storage key `paired-box`, and its log cache under `log:<session>:<n>`. An operator runs several daemons: a work server and a hobby server, perhaps two daemons on one machine, all through the same relay origin (their own; Flux is free software and others host relays too). To reach a second daemon they had to revoke the first and pair again. They want every daemon paired at once, a way to move between them, a way to unpair one on purpose, and an update that costs nobody their existing pairing.

The relay must stay ignorant (ADR 0003) and is unchanged. The protocol already has everything a device needs: a pairing link per daemon, `hello.daemon` for its name, `devices.remove` for a device to remove itself (ADR 0015), and a push subscription per device on each daemon (ADR 0013).

## Decision

1. **Several pairings, one record.** The device keeps a `pairings` record in its storage: `{ active, entries }`, an entry per daemon of `{ id, name, cache, rootPush, box }`, where `box` is the pairing record ADR 0012 already defined (relay URL, the daemon's public key, this device's keypair and id). Every change reads the record afresh and writes it whole under a Web Lock (`navigator.locks`, held across the read and the write), and a tab's changes also queue one behind another, so two tabs, or two changes in one tab, cannot write over each other's entries.
2. **A daemon is known by its room id.** `id` is `base64url(sha256(boxPub))[0..22]`, the room id of protocol.md § 1. It is derived from the daemon's static key, so it is stable for the daemon's life, the same whichever relay the link named, and two daemons on one machine have different ones. The public key itself was rejected as the id: the id goes in URLs (a notification tap, a service worker scope), and a relay that saw a daemon's public key could derive its room token and claim its host slot, which protocol.md § 2 counts on it never seeing. The room id is already public to the relay. The name is a label, not an identity: it is `hello.daemon`, saved on each connect, and may change or repeat (two daemons on one host default to the same name), so the UI adds the start of the id when two names collide.
3. **One connection open at a time.** Boot opens the daemon used last (or the one a notification named). Switching writes the open daemon's pending log cache, stashes its unsent drafts and composers, its session list and its fetched thumbnails in memory, stops its connection, clears the rest of what its screens showed (settings, devices, the runner's scrollback, which are fetched again) and opens the other, whose stash is back on screen before its `hello` arrives. Unpair waits five seconds for the daemon's answer before it counts the daemon unreachable. Pairing another daemon runs beside the open one, whose connection stays up until the new pairing is written to storage and adopted; a connection's callbacks are live only while it is the adopted one, so a pairing under way, or a daemon being let go, never touches the screens. These changes run one after another. Keeping every daemon connected was rejected: more sockets, more battery, more reconnect churn on a phone, and a store in which every piece of state would need a daemon key.
4. **Per-daemon state.** Cached logs are namespaced: the first daemon holds the bare `log:` prefix and every other daemon gets `daemon:<id>:log:`, recorded in its entry as `cache`. Drafts, composers, the session list and thumbnails are kept per daemon in memory. Device preferences (appearance, send key, switch chord, sound, split, folded strips) are the device's and are never touched by switching, pairing or unpairing.
5. **The upgrade carries the old pairing over.** On first boot of the new app, a `paired-box` record with no `pairings` record becomes the first entry, active, with `cache: 'log:'` (its cache stays exactly where it is, nothing is copied) and `rootPush: true`. The new record is written before the old key is removed, so a failure in between leaves the old key to be carried over again, never neither; a write that fails outright still opens the pairing for this boot. A storage that cannot be read at all is an error, never an empty list, so nothing is written over pairings the app could not see.
6. **Unpair, on purpose.** Settings › This device has "Unpair this device", acting on the open daemon, behind a confirm that says plainly that getting back needs a fresh `flux pair` on the daemon's machine. When the daemon is reachable the device asks it to remove this device (`devices.remove` for its own id, as Settings › Devices already allowed); either way the device then forgets the pairing, the daemon's cached logs, its drafts and its push subscription, and opens the next paired daemon or lands on the pair screen. When the daemon could not be reached it says the daemon will keep listing the device until it is revoked from another device. A `device.revoked` notice for this device, which comes only from a daemon that is open and connected as it lets go, forgets it the same way, naming the daemon that let go, and opens the next.
7. **A daemon that no longer knows this device is said so, not waited on.** A daemon revoked from another device while it was not the open one never sends the notice, and a revoked device's handshake is ignored outside a pairing window (ADR 0015), so switching to it, or booting into it, would sit on "connecting" for ever. Instead the device marks the open daemon (`unknownDevice`) when its handshake goes unanswered for 10 seconds while the relay says the daemon is there (`unanswered`: a daemon the relay knows to be missing is said by its `no_host`, which stops the wait and clears the mark), or when it answers `not_paired` (inside a pairing window). A banner under the header says the daemon no longer knows this device and offers Forget, which asks once more and then removes the pairing here alone, asking the daemon nothing since it has already forgotten the device, and opens the next daemon or the pair screen. A `not_paired` answer is not acted on by itself: forgetting a pairing on one message would lose it to a mistake, and the operator's tap costs little. The connection keeps retrying at the full backoff, and a daemon that answers after all (it was only slow) is unmarked on its `hello`. Unpair from a marked daemon asks it nothing either: after `not_paired` it says nothing more, and after an unanswered handshake it says only that the daemon did not answer and to revoke it from another device if it still knows the device, never that it will keep listing it.
8. **Push per daemon, on a worker of its own.** A browser keeps one push subscription per service worker registration, tied to one sender's VAPID key, and each daemon has its own key. So each daemon's subscription is on the same `/sw.js` registered under the scope `/push/<id>/`; no page lives there, the scope is a name. The worker reads its scope to know whose push it is: its notification tag carries the id, and a tap posts `{ type: 'flux.open', daemon, session }` to an open window (a worker that controls no page cannot navigate one), which switches to that daemon and opens the session, or opens a new window at `/s/<session>?daemon=<id>`, whose query boot reads before the router drops it. The root worker's own notifications, from the carried-over daemon before its subscription moved, open with `?daemon=root`, which boot reads as that daemon while it is still marked `rootPush`, and as the daemon used last after. A notification from a daemon that is not the open one therefore still arrives and opens in the right place, with no change to what the daemon sends. The carried-over pairing's subscription was on the root worker; once its own worker's subscription is stored on the daemon, the root one is unsubscribed, the daemon's next push to it finds it gone and drops it (ADR 0013), and `rootPush` is cleared. Unpairing a daemon unsubscribes and unregisters its worker.
9. **The UI says "daemon".** A picker at the left of the header, shown once two daemons are paired, names the open daemon and lists the others and "Pair another daemon", which opens the existing pair card (QR or pasted link) in a modal; with one daemon paired, "Pair another daemon" is in Settings › This device. The word is daemon, never box, in these controls, since several daemons can share a machine.

## Consequences

- No relay change and no protocol change. A daemon learns nothing new: it sees one more device pair, and its device list loses one when the operator unpairs.
- An existing device keeps its pairing, its cache and its notifications through the update without the operator doing anything.
- Push for a daemon starts working on a device the first time that daemon is opened there with notification permission granted; a daemon paired but never opened since the update has no subscription of its own yet.
- A browser that does not let a page register a worker under a narrower scope, or keeps only one push subscription per origin, gets no notifications from a daemon whose worker cannot register (the status bar's "Enable notifications" then says why); the carried-over pairing keeps its root subscription until its own worker succeeds, so it is never left with neither.
- The in-app notification sound only rings for the open daemon's live events, since only its connection is open; another daemon's news arrives by Web Push alone.
- The 10-second handshake wait is a guess, and "there" only means the relay holds the daemon's socket: neither the relay nor the daemon sends a heartbeat, so a daemon whose machine slept or whose network dropped without closing the socket looks present for minutes, until TCP gives up, and is marked the same way, as is one slower than 10 seconds on a very poor link. The banner therefore says the daemon may be offline or asleep as well as revoked, the mark goes as soon as the relay says the daemon is away (`no_host`) or it answers, and Forget asks once more. A first pairing whose code has expired or been used is ignored the same way, and the pair screen says the code may have expired.
- Re-pairing a daemon already paired replaces its entry in place and keeps its cache and name; the old device id is left on the daemon for the operator to revoke.
- Cancelling "Pair another daemon" while `pair.request` is in flight may leave a device the daemon accepted but this device never kept; it shows in Settings › Devices on the daemon's other devices to revoke.
- Two tabs changing the record at once are kept apart by a Web Lock where the browser has one (`navigator.locks`); without it, only one tab's changes are ordered, and a write from each at the same instant could lose one.
